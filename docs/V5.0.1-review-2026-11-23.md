# V5.0.1 UART/DMA and system review

Two independent reviewers inspected the UART/DMA implementation and its system
interactions. Reviews were read-only; the main session owned all hardware access
and changes. Both hub-connected units, 0001 and 0003, were authorized for testing.

## UART/DMA review

The reviewer found no remaining concrete driver correctness issue after the
following corrections to the release preparation and regression coverage:

| Finding | Disposition |
| --- | --- |
| The production default still selected 57600 rather than the requested rate. | Set `huart3.Init.BaudRate` to 230400. All bus boards must use the same rate. |
| DMA event races needed explicit tests. | Exercise a wrap after CNDTR sampling and TC arriving after the IRQ's HT snapshot. Assert preservation and exactly-once accounting. |
| Simplified peripheral fakes could conceal error-clearing mistakes. | Model SR-then-DR clearing, prove DR-first does not clear ORE, retain the pending-NVIC case, and simulate transfer-error DMA disable. |
| Buffer tests alone did not prove damaged commands could not execute. | Feed the production SCPI line reader an existing setter prefix followed by a UART fault/overflow. Check that the prefix is rejected and the next complete query survives, including one-byte reads and split recovery markers. |
| DE assertions needed to check actual ordering. | Check the GPIO assertion timestamp after the guard and release after simulated transmit completion; application tests retain DE through write/drain. |

Boundary coverage includes 511/512/513 unread bytes, LF at ring wrap, coalesced
completion events, a DMA copy overtaken by new data, pending UART errors after
DMA reads DR, all UART error bits, 32-bit counter wrap, and transmit timeout
bounds. The native suites passed. These tests model register behavior; they do
not measure physical DE edges or electrical contention.

## System review

The review tightened the qualification harness rather than adding production
features:

| Finding | Disposition |
| --- | --- |
| A host-provided baud label did not prove the tested image's rate. | Freeze the production binary and source hashes, match an independent clean build, upload that exact binary to both USB UIDs/hub paths, and bind the soak to the upload receipts and snapshots. Generic stress reports explicitly label an unverified baud value. |
| Setter coverage and readback could miss inputs or asynchronous application. | Rotate every GAIN/DR/MODE family across all four inputs. Poll the intended peer state while accepting only its previous or requested complete tuple. |
| DTR/reopen checks could claim cancellation without proving a pending transaction. | Use dispatch fences, a missing-peer pending transaction and a delayed real-peer single-shot conversion. Check cancellation, stale-reply suppression, actual close/reopen, and renewed RS485 traffic. |
| USB pressure could pass without reaching backpressure. | Require an observed blocked host write in every pressure round. |
| Restoration could accept truncated configuration or lose its summary on disconnect. | Require exactly four values and exact restored readbacks. Guard each close operation and preserve failure summaries. |
| Repeat-upload snapshots could redefine the stored baseline and hide corruption. | Preserve the earliest stored snapshot independently. Compare against it before and after the soak and repeat upload; retain upload history. No stored address/calibration is rewritten to make a check pass. |
| One unavailable unit could prevent restoration of the other. | Attempt each unit independently, record each outcome, then report aggregate failure. An offline regression verifies restoration of 0001 when 0003 is unavailable. |
| Comparing separate ADC conversions with a fixed tolerance could mistake conversion noise for transport corruption. | Freeze one completed single-shot conversion, compare identical direct/forwarded raw and calibrated replies, then check the calibration relation with rounding allowance. Restore continuous mode afterward. |
| A reviewed firmware hash did not bind the reviewed test procedure. | Hash the qualification scripts and require the same hashes at preparation, review, run and completion. Detect source, script, binary and baseline drift. |

Native regressions and 36 Python tests passed. The offline qualification checks
also reject a changed saved address even when a later upload snapshot contains
that same changed address.

## Hardware release gate

The release gate is a real four-hour run of the frozen production image at
230400 baud, with two active hours in each master direction. It must include
multiple durable request-ID blocks, all input/configuration families, ordered
bursts, maximum-length forwarding, simultaneous USB/ADC work, malformed input,
timeouts, DTR cancellation, actual port reopening, USB backpressure, address31,
and real input readings. Both units must then accept a repeat USB update through
the hub, pass a final functional check, and retain their original stored and
runtime settings and calibration readbacks.

The [completed qualification](V5.0.1-qualification-2026-11-23.md) passed four
hours and 3,096,581 forwarded queries, followed by both repeat hub updates and
final settings checks. The physical setup is two
nodes, approximately 50 cm of one CAT5e pair, terminated at both ends. There is
no calibrated input reference, oscilloscope timing capture, wire BER capture,
long-cable test or qualification of a fully populated 32-device bus. Configuration
canaries detect resets and unintended setters; equal unreferenced input voltages
cannot prove physical channel selection or absolute measurement accuracy.

No deferred SCPI/RS485 feature work was included.
